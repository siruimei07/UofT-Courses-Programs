# Calendar data: collection and maintenance

The site publishes **one current snapshot per campus**. There is no history selector, no
scheduled crawl and no server: a maintainer refreshes the data by hand once a year (or when the
calendar publishes a correction), reviews the candidate, accepts it and commits the result.

- Courses come from the campus Course Search (UTM: <https://utm.calendar.utoronto.ca/course-search>)
  and programs from Program Search (<https://utm.calendar.utoronto.ca/program-search>); every
  entity's detail page is then fetched.
- The academic year is read from the calendar homepage heading (`2026-2027 Calendar`), never from
  the system clock.
- Official pages are data, not instructions. Raw HTML stays in the local, git-ignored `.cache/`.

## Layout

| Path | What it is |
| --- | --- |
| `pipeline/collect_calendar.py` | Collector CLI: discovery, detail fetches, then the parser |
| `pipeline/calendar_parser.py` | Detail pages → catalog, quality report, candidate/accept logic |
| `pipeline/references.py` | Which codes in requirement text are edges (roles, code repair) |
| `pipeline/rules.py` | Requirement grammar → `Rule` AST (`src/domain/types.ts`) |
| `pipeline/cache.py` | Per-campus source cache, collection generations, hash checks |
| `pipeline/http.py` | The only network code: one User-Agent, one global throttle |
| `pipeline/campuses/` | Campus adapters (`utm.py` verified, `utsg.py` planned stub) |
| `pipeline/collect_supporting_sources.py` | Optional: official rule pages and program-area pages |
| `.cache/calendar/` | UTM source cache: `<sha256(url)>.json`, `manifest.json`, `active-run.json`, `*.candidate.json` |
| `.cache/supplementary/` | UTM supporting-source cache |
| `data/campuses.json` | Campus registry (hand-maintained; the adapters must agree with it) |
| `data/utm/catalog.json` | Published backend snapshot: courses, programs, rules, provenance |
| `data/utm/manifest.json` | Directory pages, entity lists, per-detail hash and fetch time |
| `data/utm/quality-report.json` | Coverage, unknown rules, references by role, repairs, aliases, cycles, diff |
| `data/utm/data-quality.md` | Short human summary of the quality report |
| `data/utm/subjects.json`, `official-fields.json` | Hand-curated / archived inputs; the pipeline never writes them |
| `public/data/**` | Frontend datasets generated by `scripts/build-frontend-data.ts` (committed) |

## Setup

Python 3.11 or newer (CI uses 3.14) and Node 24. From the repository root:

```powershell
python -m pip install -r requirements.txt   # pinned requests + beautifulsoup4 (pipeline/requirements.txt)
npm ci
```

Run the pipeline as a package with `python -I pipeline ...` (this is what `npm run data:collect`
does). `python -I -m pipeline.collect_calendar` cannot work: `-I` implies `-P`, so the working
directory is never on `sys.path`. `pipeline/__main__.py` puts the repository root on the path
instead. Without `-I`, `python -m pipeline.collect_calendar ...` is equivalent. Never run a file
inside `pipeline/` as a script: `pipeline/http.py` would shadow the standard library.

## Annual refresh

```powershell
# 1. Collect a fresh generation (resumable). Writes only .cache/calendar/.
npm run data:collect -- --campus utm --refresh

# 2. If it stops (network, 429, power), resume the SAME generation: run it again without --refresh.
npm run data:collect -- --campus utm

# 3. Review the candidate (see "Reviewing a candidate"), then publish it.
npm run data:collect -- --campus utm --parse-only --accept

# 4. Regenerate and check the frontend datasets, run every check, commit data/ and public/data/.
npm run data:build
npm run data:build -- --check
npm run test:py
npm run check
```

`--campus` defaults to `utm`. Without `--accept` nothing under `data/` changes: the parser writes
`catalog.candidate.json` and `quality-report.candidate.json` into the campus cache and prints a
summary. The published snapshot is replaced only when the candidate is complete, has no failures
and passes the count guard.

### Network etiquette

- One browser-like User-Agent (`pipeline/http.py`) for every request and for the `robots.txt`
  check; disallowed URLs are never fetched.
- One process-wide, lock-based throttle: request starts are at least 0.5 s apart across all worker
  threads (longer if `robots.txt` sets a crawl delay). `--workers` (1–6, default 2) only overlaps
  latency; it never raises the request rate. A full UTM collection is about 2,800 requests, so
  expect roughly 25–30 minutes.
- HTTP 401/403/429 stops that request (no retry, no bypass). Other failures retry four times with
  backoff and are recorded in the manifest; a manifest with failures is never parsed.

### Generations and the cache

Each `--refresh` starts a new collection generation (`generationId` in `active-run.json`, the
manifest and every source record). A plain run resumes the active generation and reuses only its
pages; pages from an older generation are fetched again. `--offline` never touches the network and
refuses sources from another generation. Before parsing, every manifest source (homepage,
supporting pages, directory pages, details) is re-hashed and must match the manifest.

A cache that has a complete `manifest.json` but no `active-run.json` (the original single-campus
layout) is adopted once by a normal or `--offline` run, after every source hash verifies.
`--parse-only` never migrates, initialises or rewrites the cache: it reads, validates, and writes
only its two candidate files.

## Offline re-parse (parser changes, no new collection)

```powershell
npm run data:collect -- --campus utm --parse-only            # candidate only
npm run data:collect -- --campus utm --parse-only --accept   # publish after review
```

The same cached HTML always produces the same catalog: with `PIPELINE_GOLDEN=1` the Python suite
re-parses `.cache/calendar` and compares it byte for byte with `data/utm/catalog.json`
(PowerShell: `$env:PIPELINE_GOLDEN='1'; npm run test:py`). Bump `PARSER_VERSION` in
`pipeline/calendar_parser.py` whenever parsing changes.

## Reviewing a candidate

Open `.cache/calendar/quality-report.candidate.json` (and the catalog candidate) and check:

- `failures` is empty and `coverage` shows discovered = collected for courses and programs, with
  contiguous page numbers. A drop of more than 10% in either count blocks `--accept`; investigate
  the calendar and the pager first, then use `--allow-decrease --accept` only if the drop is real.
- `snapshotDiff`: added / removed entities, `changedSource` (page hash changed) and
  `changedRequirements` (requirement text changed). `ruleCoverage.before` is copied from the
  currently published report, so accepting identical data twice still changes this field; compare
  catalogs, not reports, when you need byte identity.
- `cycles` (prerequisite references only) should stay empty or be explainable.
- `unresolvedReferences`: every referenced id that is not a course of this calendar, with its
  `status` (`external` = other campus, `unresolved` = same-campus code absent from this calendar),
  the `roles` it was found in (`required`, `unresolved`, `mentioned`) and the citing entities.
  `existingWeightTwin` marks an H/Y mismatch such as `MAT137Y5` when only `MAT137H5` exists.
- `codeRepairs`: typography the parser repaired (glued `inCSC148H5`, spaced `PHL 245H5`, missing
  campus digit `PSY325H`, bare `GGR112` with exactly one catalog match), tokens it could not
  recognise, and H/Y mismatches. Nothing is substituted except these unambiguous repairs.
- `aliases`: `(formerly X)` renumberings found in requirement text, descriptions and notes. They are
  reported for review and never substituted.
- `programCodeFallbacks`: programs whose POSt code field holds no code (the Focus programs); their
  URL slug is used as the code and the program carries `codeSource: "url-slug"`.

### Requirement roles

Only `courseIds` become graph edges. Every code in requirement text gets one role:

| Field | Contents |
| --- | --- |
| `courseIds` | Required references and alternatives that exist (same-campus catalog courses and any other-campus id) |
| `unresolvedIds` | Same-campus codes absent from this calendar (retired or misprinted), including `(formerly X)` codes |
| `mentionedIds` | Codes the text rules out (`except`, `excluding`, `other than`, `no longer be accepted` once that date has passed, `X cannot be substituted`), advisory codes (`Highly Recommended`, `Recommended Corequisite`, `(strongly recommended ...)`), codes in conditional sentences (`Students seeking ...`, `For students ...`) and codes in a field that says it has no prerequisites |

The course's own code is always dropped. `(may be taken as a corequisite)` moves the annotated
courses to the corequisite field. Advisory corequisite text is copied into `recommended`; the
official field text always stays verbatim in `rawText`.

The rule AST only references `courseIds` (`npm run data:validate` enforces it). Codes absent from
the calendar leave the AST: an OR alternative that only they satisfy is dropped, and a required one
becomes an `unknown` leaf ("cites a course code that is not in the current calendar"), so the rest
of an AND keeps its structure. In exclusions and recommendations they are simply removed (a
retired course can no longer be taken). When the roles in one sentence cannot be separated safely,
the whole rule becomes `unknown` with an explicit reason.

## Frontend datasets

`scripts/build-frontend-data.ts` projects every `available` campus in `data/campuses.json` onto
`public/data/campuses.json` and `public/data/<dataDir>/{graph,details,programs}.json`
(contract: `src/data/schema.ts`). The output is deterministic (timestamps come from the snapshot),
so an unchanged catalog regenerates byte for byte.

```powershell
npm run data:build             # write public/data/** and print sizes
npm run data:build -- --check  # exit 1 when public/data/** is stale (CI runs this)
```

`RequirementLite.ids` are the edges; `mentioned` comes from `mentionedIds`; `unresolved` is
`unresolvedIds` plus any same-campus id that is not a catalog course (moved out of `ids`, whatever
list or rule leaf it came from). Program groups keep only highlightable ids. Registry entries carry
`startSubjects` from `data/campuses.json`; for an available campus, codes the dataset lacks are
dropped with a warning.

## Supporting sources (optional)

```powershell
python -I pipeline supporting --campus utm   # reads .cache/calendar, writes .cache/supplementary
```

It collects the official rule pages and program-area (`/section/`) pages that the snapshot links
to, one primary-content hop deep, through the same User-Agent and throttle. The output is local
research material; nothing in `data/` depends on it.

## Adding a campus

1. Add the registry entry to `data/campuses.json` with `status: "planned"` (see
   `docs/data/multi-campus.md` for the UTSG values and open questions).
2. Add `pipeline/campuses/<id>.py` with a `Campus(...)` record: URLs, selectors, Drupal field
   names, title separators, year heading pattern, POSt code pattern, a cache folder of its own under
   `.cache/` (never share `active-run.json` with another campus) and its supporting slugs. Register
   it in `pipeline/campuses/__init__.py`. `tests/test_campuses.py` checks it against the registry.
3. Collect experimentally: `python -I pipeline --campus <id> --allow-planned --refresh`. Planned
   adapters refuse to run without `--allow-planned`.
4. Fix selectors and field names until the candidate has no failures, then review roles, repairs
   and unknown rules as above. Add fixture tests for the campus's own wording.
5. Write `data/<dataDir>/subjects.json`, accept the candidate, flip the adapter and the registry
   entry to `available`, run `npm run data:build` and commit `data/` and `public/data/`.

## Boundaries

Complete entity coverage does not mean every requirement is machine-understood. Whole program
admission and completion texts stay `unknown`; requirement groups are planning hints. Annual
cutoffs, cohorts, streams, elective-pool allocation, permissions, high-school courses and complex
credit combinations need manual confirmation. Other-campus and retired codes are never treated as
equivalent courses. Calendar presence does not prove that a course runs in a given term or has
seats; the snapshot has no timetable data.
